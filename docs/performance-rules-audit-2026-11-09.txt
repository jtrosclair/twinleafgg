PrizeMap performance and rules audit — November 9, 2026

Verdict
The two performance changes have strong evidence of preserving real effect execution in the tested cases. There is no newly failing functional test in the 627-spec old/new comparison, and every checkpoint and actual effect-delivery trace matched across 40 paired full solutions. This is not proof that every card combination works. The wider investigation reproduced existing rules bugs, and the phone APK is a profiling build behind newer Twinleaf rules fixes. It should not be treated as a verified release candidate.

Full solution comparison
Four existing recorded winning traces were used: Breaking Through the Wall (29 steps), Explosive Hand (20), Trapped in the Phantom Maze (21), and Something's Fishy (19). Each was replayed with ten random seeds in both old and optimized engines. Each recorded intermediate expected turn, phase, active player, prize count, and completion flag was asserted. All 80 paired-session runs reached the required human win.
There were 930 pairs of checkpoints, including loads, covering 890 ordered actions/prompt responses per engine. The comparison checked the complete reachable state graph, canonical serialized state, actual engine effect sequence, and the per-card effect-delivery sequence. It matched 23,590 actual engine effects and 2,804,080 card-effect visits on each side. Hint-only simulations were excluded from the delivery trace because reducing those simulations is the intended change. Their resulting playable-card hints were still included in the state comparisons.
A first strict comparison found differences in time-derived game-stat IDs. The rerun used the same fixed clock and seeded randomness in both engines, rather than deleting game fields from comparisons; no state or event differences remained. Log timestamp fields alone were normalized. Each engine also retained all recorded physical card choices when shuffles reordered prompt rows.
The optimized frozen engine then won 40 additional fresh sessions with ordinary randomness and clock behavior. The final current-source snapshot independently won the same 40 ordinary-randomness sessions. These are complete solution replays, not just snapshot loads.

The activation concern
None of the scanned card implementations reads playableCardIds. The event fan-out methods propagateEffect, callReduceEffect, and propagatePlayerMarkerEffect were unchanged by the optimization; checkTrainerPlay and calculatePlayability themselves were also unchanged. The optimization does not remove the actual reducer/callback/marker/prompt dispatch paths. What moved was when presentation hints are recalculated.
The source scan inspected all production engine/card TypeScript files and 55 card-specific canPlay implementations (plus the base method). The possible writes found in canPlay bodies were local counters/temporary arrays, not direct game-state updates. A runtime check called each card-specific canPlay on each of the four real starting states: 220 cases caused no state, prompt-callback, or wait-callback mutation. Counter Catcher rejected two ineligible positions without mutation, as expected.
Focused behavioral scenarios ran against the old frozen engine, optimized frozen engine and final newer source. Eleven scenarios passed in each version, including Lumineon's on-bench search, Path to the Peak suppression, Munkidori's damage movement and required Darkness Energy, independent legitimate uses of two Munkidori copies, end-turn marker cleanup, Exeggcute activation from discard, Toedscruel recovery prevention, Gengar activation from discard, Pyukumuku activation from hand, and Manaphy bench protection with/without Ability lock.

Two additional real rules bugs reproduced in all three versions:
1. Crobat V DAA permits a second physical copy to trigger Dark Asset in the same turn. Accepting the second prompt draws the hand back from five to six. The printed restriction is shared across all Dark Asset uses, not per physical card.
2. Pyukumuku FST permits a second physical copy to use Pitch a Pyukumuku in the same turn. The printed restriction is also shared across copies.
Both handlers test player.marker.hasMarker(markerName, this), and Marker matches the physical source object when supplied. That checks only that copy's marker. A focused correction should enforce the player-wide allowance for these named abilities while preserving per-Pokemon allowances such as Munkidori. Regression coverage should retain the successful two-Munkidori scenario as a counterexample to globally suppressing repeated abilities.
These two newly reproduced bugs were not fixed during this audit; their failing assertions and before/after reproductions are in the packet.

Existing copied-handler limitation
The two whole-suite failures use adversarial handlers with unlabelled attack-owned and Ability-owned branches. One incorrectly inherits an unrelated defensive passive after copied Harden; another incorrectly adds an Ability-owned bonus to a copied initial AttackEffect. They reproduce before and after the optimization and are already acknowledged in Twinleaf's sync record. Ordinary named-card and copy/marker regressions continue passing, but generic copied-attack ownership remains an architectural limitation. A durable fix needs explicit branch ownership; reducing hint scans neither causes nor solves it.

Recommendation for Twinleaf
Keep the measured performance changes for integration: the tested engine event path still executes, and the speedup comes from avoiding repeated speculative work. Rebuild the app from a single reviewed current source snapshot, including its existing callable-function and rule fixes, then run this solution/activation audit against that release build. Track or resolve the Crobat/Pyukumuku shared limits and the known copied-handler limitation explicitly. Do not promote the older profiling APK on the strength of the original 294-test claim alone.
